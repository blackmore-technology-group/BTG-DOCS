BTG Studio — Public Operator Manual

Practical steps, checkpoints and failure handling for the current research implementation.

A design and verified local research guide, not a declaration of production capability.

Before starting

Use the authorized Windows Studio application and a research-only account. Confirm that the project goal can be reduced to verifiable acceptance tests. The current Studio account is not yet confirmed as a production-wide BTG single sign-on.

Design and connect

Open the interlocking Circuit workspace. Describe the requested system in plain language with target platform, outputs and performance criteria. Select existing typed pieces and connect only compatible interfaces. Review the missing-parts report before invoking NIKI. Do not assume an attractive canvas indicates executable wiring.

Research and verify

Require the model's proposed tool identifiers, missing sources, candidate components, testing procedure and explicit blockers. A rejected or timed-out model response must remain a failure. Verify actual data collection, restricted execution results, independent acceptance and source-bound receipts. Grand Forks forestry cutblock data alone is not a qualified drone flight or ecological analysis result.

Instrument-controlled execution

Check that the intended right explicitly authorizes the particular project, subject, device, version, resource limit and purpose. Reject expired, replayed, revoked, unknown or mismatched entitlements. Research-level instrument adapters are not payment verification or exchange settlement.

Release and troubleshooting

Before any finished-system claim, confirm build artifacts, startup, project export, actual UI controls, real data and full end-to-end functionality on the intended OS/device. Keep error cases, tests, dependencies and screenshots. The 24 October eight-test integrated rights suite has two errors; do not mark the complete workflow as passing or conceal these failures.
